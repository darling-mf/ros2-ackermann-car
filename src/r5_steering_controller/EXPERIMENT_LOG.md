## 0. 为什么用这个循环

```
功能(带意图) → 预测(写数字) → 测试 → 数据 → ┬─ 符合预测 → 固化/下一轮
                                            └─ 违背预测 → 破案 → 修复 → 复测 ─┐
                                                     ▲______________________|
```

跳过任何一步的代价（本次全部真实发生）：

| 跳过 | 代价（实录） |
|---|---|
| 不写预测 | 第一版限幅"存在但失效"，车照样跑——没有预期数字就发现不了半失效 |
| 不量化数据 | "车动了"和"限幅生效"无法区分；破案时没有锚点（2.484 vs 0.8 一眼定位"完全没限"） |
| 不复测 | Round 2 的量纲 bug 就是 Round 1 修复**引入**的——修复本身也是新代码 |
| 不控单变量 | Round 4 若同时改参数和环境，永远归因不到"撞家具" |

## Round 1：参考层限幅 → 限幅被父类覆盖

| 环节 | 内容 |
|---|---|
| **功能** | 加速度限幅 v1：在调用父类**之前**夹 `reference_interfaces_[0]`（参考层方案，直觉上"限输入最干净"） |
| **预测** | vx 阶跃 0→0.5 后，`/odom` 峰值加速度 ≤ 0.8 m/s²（判据 0.8×1.25+0.05 留传递误差余量） |
| **测试** | `ros2 run car_bringup acceptance_test.py --vx 0.5` |
| **数据** | ❌ 峰值 **2.484**（超限 3 倍）；稳态 vx 0.500 ✓。测试 2/3 意外 PASS |
| **破案** | 矛盾点：限幅器存在 + 车正常跑 + 峰值超限 → 说明限幅"在但没管用"。读父类源码发现 `reference_interfaces_` 的真实生命周期：**每个周期开头从订阅者无条件重载、结尾清 NaN**。子类写在父类重载之前 = 写完就被覆盖。佐证：测试 2 的稳态 ω=0.900 恰好是父类 `max_steering_angle` 机械限位的换算值——PASS 是父类在兜底，不是新功能在工作 |
| **修复** | 架构重构：三个功能全部移到**命令层后处理**（父类写完 command_interfaces_ 之后、resource_manager 读取之前"读出→限幅→写回"，这段窗口确定生效） |
| **教训** | "你写的代码"≠"被执行的数据流"。**交叉引用**（功能 A 失效 + B 正常）通常说明你以为在控制的变量和实际被读的变量不是同一个 |

## Round 2：命令层重构 → 量纲写反

| 环节 | 内容 |
|---|---|
| **功能** | v2：命令层斜坡 `raw = clamp(raw, last−dw, last+dw)`，`dw = max_accel **×** r × dt` |
| **预测** | 峰值 ≈ 0.8，0→0.5 m/s 约 0.63 s |
| **测试** | 同上 |
| **数据** | ❌ 峰值 **0.005**，稳态 vx **0.003**——车几乎不动。**FAIL 的方向反了**（上轮限不住，这轮限过头） |
| **破案** | 手算：dw = 0.8×0.0325×0.02 = 0.00052 rad/s/周期 → 爬到 15.4 rad/s 需要 **591 秒**——数值本身在喊"斜率错了"。正解：v=ωr ⇒ dω/dt = a**/**r（不是 ×r），差 r² ≈ 947 倍 |
| **修复** | `dw = max_accel_ / r_wheel * dt`，并在该行写上量纲注释 `[m/s²]/[m] = [rad/s²]` |
| **教训** | 修复本身是新代码，**必须复测**（本条就是 Round 1 修复引入的）。一切物理换算：带单位注释 + 幅值 sanity check。符号对、幅值错一千倍的 bug 只有测试能抓 |

## Round 3：复测基线（vx=0.5）—— 首次全绿

| 环节 | 内容 |
|---|---|
| **测试** | acceptance_test --vx 0.5 --max-steer-rate 9.5 |
| **数据** | ✅ 峰值加速度 **0.889**/0.80；稳态 ω **0.904**/上限 1.069；峰值 \|dφ/dt\| **9.63**/9.5 |
| **解读（PASS 的两个数字为什么不"完美"）** | ① 0.889>0.8 仍 PASS：限幅器限的是**指令**，`/odom` 是 FK 测量链（轮速+滚动均窗+20Hz 采样差分），0.889 = 0.8 × (1+传递误差)。判据留 25% 余量就是给这条链路。② 0.904<1.069：稳态转弯的轮胎刮地（scrub）让实际车速低于指令，ω=v·tanφ/L 随 v 缩水——**这是物理不是 bug**，真车同样如此 |
| **固化** | 该场景定为回归基线 |

## Round 4：高速预测实验（vx=1.0）→ 假故障

| 环节 | 内容 |
|---|---|
| **功能/预测** | 预测 a_lat 限幅在高速"接管"：vx=1.0 时 φ_cap 从 0.235（机械）切到 0.220（a_lat），ω 上限从 1.069 → **2.000**；峰值加速度仍 ≤ 1.05 |
| **测试** | acceptance_test --vx 1.0 |
| **数据** | ❌ 双 FAIL：加速度峰值 1.155；稳态 ω 仅 1.057。补充采样：vx 曲线在 0.3~0.7 间振荡，dv/dt 出现 ±5 |
| **破案** | 先怀疑控制器（命令层刚重构）→ 逐项排查无果 → 转向**环境假设**：`gz model -m ackermann_car -p` → 车在 **(-1.26, 1.01) yaw −0.79** ——之前几轮测试把它开进了房间家具堆，顶住墙、轮子打滑，一切"异常数据"都是墙给的 |
| **修复** | `gz model -m ackermann_car -x 0 -y 0 -z 0.05 -R 0 -P 0 -Y 0` 复位 |
| **复测** | ✅ 三项 PASS：0.953 / **1.754 vs 2.000**（a_lat 绑定切换被证实）/ 8.61 |
| **教训** | **被测对象的状态是实验变量**。连续实验之间必须复位位姿/速度/里程计，否则测的是"上次实验的残留"。破案顺序：先查环境（免费），再查代码（昂贵） |

## Round 5：修改预测闭环（rate 9.5→1.5）—— 预测能力的标定

| 环节 | 内容 |
|---|---|
| **修改** | `r5.max_steer_rate: 9.5 → 1.5`（单变量） |
| **预测（跑之前写下）** | 峰值 \|dφ/dt\| ≈ 1.5×(1±5%)；0.235 rad 满舵阶跃需 0.16 s 到位；转向瞬态车"先直后弯"外甩 |
| **测试** | acceptance_test --max-steer-rate 1.5 |
| **数据** | ✅ 峰值 **1.577**（预测命中，偏差 5.1% 来自关节跟踪+采样差分）；其余两项不敏感（符合"单变量"预期） |
| **意义** | 这轮没有 bug——它的价值是**标定你对代码的预测能力**。预测命中率就是你"读懂代码"的可测量定义 |

## 2. 可复用的破案决策树（从本次提炼）

```
测试数据违背预测
 ├─ 数据"恰好等于另一个已知机制"的输出？
 │    → 有别的组件在兜底/覆盖（Round 1：父类 max_steering_angle）
 ├─ 数值离谱地小（差 100~1000 倍）？
 │    → 量纲/单位换算（Round 2）
 ├─ 数据混沌振荡、不可复现？
 │    → 先查环境：被测对象位姿、残留运动、干扰（Round 4）
 ├─ 数据"接近但系统性偏离"？
 │    → 物理效应（scrub/摩擦/滤波），更新预测模型而不是改代码（Round 3）
 └─ 修复后必须复测 + 跑回归基线（Round 2 就是修复引入的新 bug）
```

## Round 6：实验台设计决策（写代码前的四个"为什么"）

| 决策 | 为什么 | 替代方案及否决理由 |
|---|---|---|
| 独立 Python 节点，绕过 Nav2 controller_server | 对比实验要**控制变量**：Nav2 的重规划/恢复行为/velocity_smoother 都会污染数据；独立节点让"同一路径、同一速度、同一底盘"成立 | 直接写 Nav2 插件：工作量大 10 倍且调参耦合，阶段一先学算法本体 |
| 路径**相对当前位姿生成** | 复现性：无论车在哪，`--offset 0.3` 都产生相同的初始条件；也顺带规避了"teleport 后 ros2_control 里程计滞后"的坑（闭环跟踪全程在 odom 系内，相对几何不变） | 固定世界坐标路径：每次都要把车摆回同一位姿 |
| 误差定义统一：e（横向，左正）、Δψ（航向差，左正）、δ（左正） | 三种论文原文的符号约定各不相同，统一后才能公平对比；所有修正项符号由一个约定推出 | 各用各的论文符号：必然出现"符号对不上"的经典惨案 |
| 最近点投影带**单调进度窗口**（只向前找） | 防止投影跳到路径远处/自身交叉处造成误差跳变——所有真实 tracker（Nav2 的 MPPI/RPP）都有这个机制 | 全路径全局最近点：S 形路径上会跳段 |

## Round 7：三个 bug 的循环实录

### 7.1 DDS 发现延迟 → "没收到 /odom"
- **功能**：启动后 `spin(1.0)` 等一秒就检查 /odom。
- **预测**：控制器 active、/odom 50Hz，1 秒足够。
- **数据**：❌ `错误：没收到 /odom`——但 `ros2 topic echo /odom` 明明有数据。
- **破案**：话题存在但**订阅匹配没建立**——DDS discovery 在守护进程重启后要 2~3 秒，固定等 1 秒是竞态。
- **修复**：改成带 5s 超时的等待循环。
- **教训**：**"等待"逻辑本身要带超时与重试语义**，固定时长等待 = 埋竞态。

### 7.2 Riccati 转置放错边 → numpy shape 报错
- **功能**：DARE 迭代 `P = Q + AᵀPA − (AᵀPB)(R+BᵀPB)⁻¹(BᵀPA)`。
- **数据**：❌ `ValueError: solve: Input operand 1 has a mismatch... (size 2 is different from 1)`。
- **破案**：维度核对——AᵀPB 是 (2×1)、(R+BᵀPB)⁻¹ 是 (1×1)、BᵀPA 是 (1×2)，我写的乘法顺序把 (1×2) 当成了被求解对象。
- **修复**：`Pn = Q + AᵀPA − BtPA.T @ solve(R+BᵀPB, BtPA)`。
- **教训**：**shape 即类型**。矩阵代码先在纸上写维度注记再写乘法；numpy 的 shape 检查是免费的第一道测试。且此 bug 是**离线抓的**（单独验证 DARE，不占仿真时间）——能离线验证的模块绝不进仿真调。

### 7.3 LQR 阻尼不足 → 离线权重扫描
- **数据**：离线闭环模拟初始误差 0.3m，3s 后 e=−0.0675（超调 22%），ζ≈0.4。
- **破案**：k2（航向增益）偏小 → 阻尼不足。扫 `Q=diag(q_e,q_ψ), R` 四组。
- **修复**：默认 (25, 4, 25) → K=[0.973, 0.613]，k1 提高后初始 δ 直接进机械限位饱和区——瞬态由限位主导，LQR 负责"饱和之后的收敛"。
- **教训**：**LQR 的调参是显式的（Q/R → K → 极点）**，对比 Stanley 只有一个 k、PP 只有一个 l_d——这是 LQR 工程上最大的优势：性能目标可写进代价函数。

## Round 8：对比实验数据（同底盘、同路径、同速度）

直线收敛实验（路径在车左侧 0.3m，v=0.3 m/s，3m 长）：

| tracker | 收敛时间 | 稳态 RMS\|e\| | 稳态 max\|e\| | RMS\|Δψ\| |
|---|---|---|---|---|
| Pure Pursuit (l_d=0.35) | **2.77 s** | **0.0224 m** | 0.1049 m | 6.71° |
| Stanley (k=1.0) | 3.11 s | 0.0298 m | 0.1133 m | **5.38°** |
| LQR (25,4,25) | 3.84 s | 0.0470 m | 0.1534 m | 6.19° |

正弦跟随实验（A=0.3m，λ=3.0m，v=0.3 m/s，起点在路径上）：

| tracker | RMS\|e\| | max\|e\| | RMS\|Δψ\| |
|---|---|---|---|
| Pure Pursuit | **0.0161 m** | 0.0627 m | 3.30° |
| Stanley | 0.0163 m | **0.0467 m** | 3.46° |
| LQR | 0.0215 m | 0.0765 m | **2.41°** |

### 数据解读（谁"赢"取决于指标——这是本实验最重要的结论）

1. **PP 的 RMS 领先要打折看**：前视点机制天然"切弯/预瞄"，在缓曲率路径上 RMS 好看；但 PP **没有收敛性保证**，l_d 调坏会振荡——它在两个实验里都拿了 RMS 第一，不代表它是更好的控制器，代表它"预瞄占了便宜"。
2. **LQR 的 RMS 落后要打折看**：它的增益按设计速度 v=0.3 调度，但 R5 控制器有 0.8 m/s² 的加速斜坡——前 0.6s 实际 v 远低于设计值，模型失配让 LQR 收敛最慢（3.84s），瞬态被算进 RMS 窗口。**实车 LQR 一定配增益调度**（按 v 实时解 K），这不是缺陷是教学简化。
3. **LQR 的航向 RMS 全场最佳（2.41°）是曲率前馈的功劳**：δ_ff=atan(Lκ) 把"已知曲率"直接喂给转向，反馈只修残差；PP/Stanley 没有前馈槽，全靠反馈追，航向滞后 3.3~3.5°。**前馈管已知、反馈管未知**——这一句就是第三章全部实战的浓缩。
4. **所有误差都在厘米级**：下限由 R5 控制器的斜坡/限幅 + 轮地物理决定，而不是 tracker 算法。对比实验的分辨率要和执行链路的噪声地板匹配。
